---
description: "Rerun testing apps and reconcile Testing and Verified tickets with current deep verification"
---
Load `tickets-zordon` ({{SKILLS}}/tickets-zordon/SKILL.md). Use `node {{SKILLS}}/tickets-zordon/scripts/shifu.mjs` below, located under the loaded skill. Read the words typed after the command as arguments, without evaluating them as shell text. `--help` shows `/analyse-shifu`, `/analyse-shifu F191`, `/analyse-shifu F190 F191`, and `/analyse-shifu --configure`. Use `select analyse [IDs]` to read the current Testing and Verified tickets, defaulting to both states. Report unavailable IDs. Hosts with argument completion can suggest the `eligible` IDs.

1. Discover available testing apps. `apps` detects built-in local runners such as root npm test scripts, test scripts in tracked nested packages, and configured pytest. A nested npm target runs from its package directory. For other predefined host testing adapters currently available, write a temporary array of `{id,label}` entries and pass it to `apps <available-host-apps.json>`. Use stable lowercase IDs and only include adapters for which the host has an actual test execution tool and supported repo setup. Do not list arbitrary commands, unconnected apps, or generic review agents as apps.
2. If the repo has no saved choice, or `--configure` was requested, ask the user to choose one or more available apps. Persist the choice with `configure <available-host-apps.json|-> <app IDs>` (`-` means built-ins only). `--configure` alone updates the choice without running analysis. Shifu saves the choices and review cache in `skillator/shifu.json` within the Git common directory so linked worktrees share the repo configuration. If a saved app is unavailable, identify it and offer to reconfigure. Until changed, retain it and treat any required check that relies on it as unverified. If no apps are available yet, explain which runners are supported and what capability is missing. Keep all JSON inputs in the host's temp directory outside the repo.
3. On each analysis run, run all applicable selected app checks afresh against the current repo. For a local app run `test <app ID>` and retain the observed verdict and output. For a host app invoke its actual test execution tool now with the repo and the relevant ticket scope. The adapter must return PASS, FAIL, or OWNER, with the app, applicable ticket IDs, checks run, and current evidence for each verdict. A repo-wide check can be run once and used for the tickets it covers. Record why an app is inapplicable when it has no required checks for a ticket. An unrun required check, missing evidence, unavailable applicable app, or no applicable app evidence blocks PASS. Preserve owner-only acceptance criteria even if an app passes.
4. After the app checks, capture `snapshot <ID>` for each selected ticket. Reuse a persisted deep result only if `cached` is present. For all remaining IDs, run `/verify-shifu --deep <IDs>` as the deep phase, following its instructions and deferring board writes until the combined verdict. This allows analysis of Testing and Verified rows without premature promotion. The identity hashes current Git-visible files, including tracked and nonignored untracked files and worktree edits, the ticket's implementation commits, and its authored text. It excludes board states, verdict annotations, the archive, Shifu state, and reports. Changes elsewhere in the repo can conservatively invalidate review. Fresh app results always matter even when the deep result is reused.
5. For each ticket run `combine <evidence.json>` with `{id, owner, apps:[{id, verdict, evidence}]}`. Supply the owner's outstanding requirement as `owner` when present. Supply one row per selected app, with PASS, FAIL, OWNER, or N/A with a reason for an inapplicable app. The helper rechecks the deep identity and requires PASS both for the matching deep result and for all applicable required app checks, with at least one app providing current evidence. Apply each overall verdict with `ticket-meta verify <ID> pass|fail|owner <evidence>` and read the board back. Pass one line of evidence without parentheses or asterisks. PASS promotes to Verified, and FAIL or OWNER leaves or returns the ticket to Testing. Use `report <run.json>` for the combined report and, if a deep verification ran, its separate verification report with the actual resulting board states. Link the reports and note any cached deep results.
